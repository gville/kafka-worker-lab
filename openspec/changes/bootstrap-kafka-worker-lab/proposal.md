# Proposal

## Why

The repository currently contains only the project description and OpenSpec scaffolding; there is no runnable system. The laboratory needs a complete first version so a learner can run a payment flow locally and observe Kafka event delivery, the transactional outbox, idempotency, retries, dead-letter handling, worker coordination, observability, and fault injection end to end.

## What Changes

- Add a reproducible local runtime using Docker Compose with a single-node Apache Kafka 4.x broker in KRaft mode (external listener `localhost:9092`, internal listener `kafka:9093`) and one PostgreSQL instance containing seven logical databases: `payments_db`, `payment_worker_db`, `provider_db`, `observability_db`, `analytics_db`, `notification_db`, and `workers_api_db`. Topic auto-creation is disabled; topics are created explicitly. Producers use `acks=all` and idempotence with `min.insync.replicas=1`. All services expose health and readiness endpoints and emit structured JSON logs to stdout/stderr.
- Add a Payment API that accepts payments, enforces a global `Idempotency-Key` namespace with no expiry in v1, returns the original payment for identical content, returns HTTP 400 for a missing header, returns HTTP 409 for conflicting content, returns HTTP 422 for invalid content when the header is present, writes payment records plus outbox records in one `payments_db` transaction, and returns HTTP 202 after the PostgreSQL commit without waiting for Kafka.
- Add an Outbox Publisher that publishes committed outbox records as `PaymentRequested` events to `payments.events` with at-least-once delivery and marks a record published only after broker acknowledgement. It reports pending outbox records as point-in-time snapshots in its existing structured JSON logs, counted from the `payments_db` outbox table with its restricted access. Snapshots are emitted on every polling cycle, including retry cycles while Kafka is unavailable, and immediately after a successful publish mark in PostgreSQL, even when the count is unchanged; no real-time or seconds-based freshness is guaranteed and no new endpoint, metric, service, database, or configuration is introduced.
- Add a Simulated Payment Provider with a global scenario selection for `normal`, `slow`, `timeout`, HTTP 503, permanent rejection, and uncertain result. The selected scenario applies to all incoming charge requests until changed or reset; per-payment targeting is deferred. Charges are idempotent by `paymentId`.
- Add a Payment Worker that consumes `PaymentRequested` events, calls the provider, makes three total attempts with 1-second and 2-second backoff, publishes `PaymentApproved` or `PaymentRejected` events, and routes failures to `payments.dlq`. Exhausted processing failures use `failureCategory=processing` and become terminal `FAILED`; invalid or version-incompatible events use `failureCategory=validation`, are dead-lettered directly, and do not produce `FAILED`.
- Add an Observability API whose internal consumers own the payment read projection, event history, operational dead-letter records, and `once` fault records in `observability_db`, consuming `payments.events` and dead-letter records, setting `FAILED` only for `processing` dead letters, exposing `validation` records for operational inspection, and deduplicating DLQ records by the approved identity strategy; its HTTP endpoints are read-only payment, consumer-group, and operational query views and use no cross-service SQL.
- Add Notification Workers that consume `PaymentApproved` and `PaymentRejected` events and emit simulated, log-only notifications with structured JSON lifecycle logs, and Analytics Workers that consume `PaymentRequested`, `PaymentApproved`, and `PaymentRejected`, deduplicate by `eventId`, update metrics transactionally, persist cumulative `payments_requested_total`, `payments_approved_total`, `payments_rejected_total`, and per-currency `payments_approved_amount_total` metrics in `analytics_db`, and expose a derived approval rate.
- Add a Workers API that workers poll with 5-second heartbeats, receiving pending commands and per-worker-instance fault configuration in heartbeat responses, with a 15-second offline threshold, exactly four injectable fault types (`processing-error`, `slow-processing`, `crash-before-processing`, `crash-after-processing`), once/always fault modes, distinct clear-fault and delete-configuration operations, same-identity resubmission that updates the active configuration while preserving the `faultId` and once history, no callbacks or control addresses, and a dedicated `workers_api_db` where PostgreSQL atomically enforces uniqueness of non-deleted `clientConfigKey`-to-`faultId` associations at creation time while active configuration remains volatile. Concurrent creations for the same absent key yield one winner and HTTP 409 Conflict for each loser without an extra `faultId` or association change.
- Organize requirements as nine capability specs instead of one system-wide specification.
- Implement in this order: local infrastructure; Payment API and Outbox Publisher; Simulated Payment Provider; Payment Worker; Observability API; Notification and Analytics Workers; Workers API and fault experiments.

Out of scope for this change: the dashboard, Grafana, Loki, Alloy, and any cloud, Kubernetes, or additional infrastructure. These remain deferred.

## Approved Architecture

These decisions are fixed for this change and are not reopened as questions:

1. **PostgreSQL**: one local instance with exactly seven logical databases: `payments_db`, `payment_worker_db`, `provider_db`, `observability_db`, `analytics_db`, `notification_db`, and `workers_api_db`. `payments_db` has the Payment API as its sole logical owner for its payments, idempotency, and outbox data. The Outbox Publisher has authorized technical access restricted exclusively to the `payments_db` outbox table to query pending publications and mark records published after Kafka acknowledgement; it has no access to the payments or idempotency tables, and no other service has access to `payments_db`. `workers_api_db` belongs exclusively to the Workers API and persists `clientConfigKey`-to-`faultId` associations and their deletion status, with PostgreSQL atomically enforcing uniqueness of non-deleted associations at creation time; it does not store worker `once` records or general configuration state.
2. **Kafka**: `payments.events` carries `PaymentRequested`, `PaymentApproved`, and `PaymentRejected`; `payments.dlq` carries exhausted processing events and validation-failed events. Both topics use 3 partitions and replication factor 1. `payments.events` retains events for 7 days; `payments.dlq` retains events for 30 days.
3. **Event envelope**: `eventId`, `eventType`, `schemaVersion`, `paymentId`, `correlationId`, `occurredAt`, `producer`, and `data`.
4. **Payment status**: the Observability API owns the payment read projection and history in `observability_db`. Statuses are `PENDING`, `APPROVED`, `REJECTED`, and `FAILED`. `REJECTED` means the provider explicitly rejected the payment for business reasons. `FAILED` means processing could not complete after retries were exhausted and the request was sent to `payments.dlq`. Validation dead letters do not change payment status and remain inspectable. A terminal status is not overwritten by later or delayed lifecycle events: a delayed `PaymentRequested`, `PaymentApproved`, or `PaymentRejected` consumed after `FAILED` leaves the projection `FAILED`. The Payment API does not consume result events to update its own payment status.
5. **Observability access**: the Observability API serves read-only HTTP query views from its own projection database and uses no cross-service SQL; its internal Kafka consumers write projection, history, operational dead-letter records, and `once` records to `observability_db`.
6. **Workers API**: workers poll it through heartbeats and receive pending commands in heartbeat responses. No HTTP callbacks or worker control addresses.
7. **Fault injection**: per-worker-instance configuration with exactly four injectable fault types: `processing-error`, `slow-processing`, `crash-before-processing`, and `crash-after-processing`. Modes are `once` and `always`. `pause` and `resume` are control commands, not fault types. Each worker persists `once` records in its own logical database, identified by worker type, `faultId`, Kafka topic, partition, and offset; the record is registered atomically immediately before the fault's injection point, and only the execution that registers it applies the fault. If the process stops after registration but before execution, the record remains and redelivery skips the fault, so `once` guarantees at most one execution per message but not that the fault executes. Each fault configuration has a client-provided `clientConfigKey` that names the logical rule and a UUID v4 `faultId` that the Workers API generates. The Workers API stores the `clientConfigKey`-to-`faultId` association and its deletion status in `workers_api_db`, its exclusive database, and the association survives Workers API restarts. `clientConfigKey` is globally unique within Workers API across non-deleted associations, and PostgreSQL enforces that uniqueness atomically at creation time rather than relying only on Workers API pre-validation. Concurrent creations for the same absent key produce one winner that receives the created association's `faultId` and HTTP 409 Conflict for each loser, with no additional `faultId` and no change to the winner's association; a creation-race 409 is distinct from an identity-conflict 409. Reconfiguring a non-deleted rule requires reusing its `clientConfigKey` and recovers its `faultId`; a new rule uses a key with no non-deleted association, including a deleted historical key, and receives a new UUID v4 `faultId`. An active key submitted with a different `workerType` or `faultType` receives HTTP 409 Conflict, leaves the association unchanged, and creates no `faultId`. If both fields match, the request updates the same logical configuration: the original `faultId` and association are preserved, no new association or UUID is created, and the active in-memory parameters defined by the contract are updated, including `mode`, worker instance target when applicable, `slow-processing` duration when applicable, and any other parameter already defined for that `faultType`. Changing between `once` and `always` in either direction does not delete, modify, or reset historical `once` records. The updated configuration remains volatile and is not restored after a Workers API restart. Clearing a fault removes only the active in-memory configuration and leaves the association active and non-deleted in `workers_api_db` with the same `faultId`; reconfiguring with the same key recovers that `faultId`. Deleting a configuration also removes any active configuration, marks its association as deleted without changing its `faultId`, and frees the key for a new rule with a new UUID v4 `faultId`. Clearing or deleting a configuration does not delete or modify worker `once` records, and historical records keep their original `faultId`. Keys are 1 to 128 ASCII letters, digits, hyphen (`-`), underscore (`_`), or dot (`.`), with no spaces and case-sensitive comparison. A missing or invalid key receives HTTP 400 Bad Request, and none of these errors changes an association or generates a `faultId`. `always` faults keep applying until cleared or the Workers API restarts, write no record, and their active configuration is volatile; no automatic cleanup is added in v1. `slow-processing` is available to all four worker types (Payment Worker, Notification Workers, Analytics Workers, and the Observability consumers of events and dead-letter records), applies a configurable delay with a 5-second default before processing, and does not alter retry or offset-commit policies; in the Payment Worker it is applied before the provider call. Fault injection is separate from provider scenario selection and does not change the provider's global scenario.
8. **Retries**: three total attempts with 1-second and 2-second exponential backoff. No jitter.
9. **Provider scenarios**: `normal`, `slow`, `timeout`, HTTP 503, permanent rejection, and uncertain result. Scenario selection is global to the provider and applies to all incoming charge requests until changed or reset; per-payment targeting is deferred. Provider idempotency uses `paymentId`.
10. **Idempotency keys**: one global key namespace; no expiration in v1. The same key with the same request content returns the original payment. The same key with different content returns HTTP 409 Conflict. A missing `Idempotency-Key` header is a request-structure error and returns HTTP 400 Bad Request. Invalid request content with the header present returns HTTP 422 Unprocessable Content.
11. **Payment API acknowledgement**: after the atomic `payments_db` transaction commits, the API returns HTTP 202 Accepted without waiting for Kafka publication or outbox processing.
12. **Dead-letter semantics**: `failureCategory=processing` covers processing failures, including an injected `processing-error`, which is applied before the Simulated Payment Provider is called so the provider is not called before the forced error behavior completes. After the approved three total attempts with 1-second and 2-second backoff, the event is dead-lettered with `failureCategory=processing` and `attempts=3` and produces terminal `FAILED`; `failureCategory=validation` covers invalid or version-incompatible events, records `attempts=0`, performs no provider call, and does not produce `FAILED`. Original offsets are committed only after broker acknowledgement of the DLQ publication. A crash between publication and commit may duplicate DLQ records; Observability deduplicates them using the approved identity and recovery-limit strategy in decision 21.
13. **Kafka runtime**: Apache Kafka 4.x in KRaft mode with a single broker; external listener `localhost:9092`, internal listener `kafka:9093`; automatic topic creation disabled. Producers use `acks=all`, idempotence enabled, and `min.insync.replicas=1`. Health checks use broker metadata.
14. **Analytics consistency**: Analytics Workers consume `PaymentRequested`, `PaymentApproved`, and `PaymentRejected`, deduplicate lifecycle events by `eventId`, and update their metrics transactionally.
15. **Logging and endpoints**: every service emits structured JSON logs to stdout/stderr and exposes health and readiness endpoints. Loki, Grafana, Alloy, and dashboards remain out of scope.
16. **Local security posture**: the first local version has no service authentication and no TLS, is intended exclusively for local development, and does not expose services to external networks. Kafka and PostgreSQL are reachable from containers and, when needed, from the Mac through host ports published exclusively on localhost. Kafka listeners may bind `0.0.0.0` inside the container to accept Docker connections, but that does not authorize publishing host ports on all interfaces. No production security mechanisms are included in this stage.
17. **Go module layout**: the repository uses one Go module at its root with a single `go.mod`; `go.work` and multiple Go modules are excluded. Each service has its own `main.go` and can compile, run, test, and deploy independently while retaining its own responsibilities and business logic. Shared packages are limited to genuinely common technical concerns such as Kafka and PostgreSQL connectivity, structured logging, and shared event contracts and serialization, with narrow APIs. Services depend only on what they need. Business logic is not shared between services and premature abstractions are excluded. Shared internal packages live under `internal/`; `pkg/` is not created without a concrete need.
18. **Notification logging**: the Notification Worker uses the project's structured JSON logging to stdout. It logs `event_received`, `event_processed`, `notification_simulated`, `event_ignored_duplicate`, and `event_processing_failed`, including `timestamp`, `level`, `service`, `workerId`, `eventId`, `paymentId`, and `eventType` when available. Logs distinguish reception, processing, duplicate detection, and errors. `notification_simulated` indicates only that a notification was simulated; it does not imply a real email or SMS. `notification_db` is used exclusively for `once` fault records; no notification persistence and no persistent business-event deduplication are introduced, and the approved in-memory deduplication strategy is unchanged.
19. **Analytics initial metrics**: the approved v1 metric set is `payments_requested_total`, `payments_approved_total`, `payments_rejected_total`, and `payments_approved_amount_total`. The counters update from `PaymentRequested`, `PaymentApproved`, and `PaymentRejected` respectively, and approved amounts are grouped by currency. Metrics are cumulative with no time windows in v1. Amounts remain separated by currency and are never converted. `eventId` deduplication and the transactional update of processed records plus metrics are unchanged. No additional metrics are added.
20. **Worker heartbeat parameters**: workers send a heartbeat every 5 seconds. The Workers API marks a worker `offline` when more than 15 seconds have elapsed since the last heartbeat it received from that worker.
21. **DLQ identity and recovery limit**: when the original event contains `eventId` and the record has `failureCategory`, the DLQ identity is `eventId + failureCategory`. When `eventId` is absent, the identity is `sourceTopic + sourcePartition + sourceOffset + failureCategory`. A missing `failureCategory` defaults to `unknown`, including when both `eventId` and `failureCategory` are absent, in which case the original Kafka coordinates plus `unknown` are used. If neither `eventId` nor reliable original coordinates can be recovered, identification and deduplication are not guaranteed: a critical error is logged, the record is not incorporated into the Observability projection, the offset is committed so processing continues with later messages, and the original record remains in Kafka subject to the configured retention. No additional recovery mechanisms or artificial identifiers are introduced. The design does not guarantee automatic recovery from every imaginable failure.
22. **Analytics state treatment and approval rate**: every requested payment increments `payments_requested_total`. Pending and failed payments count only as requested and do not increment approved or rejected counters or the approved amount. An approved payment increments `payments_approved_total` and its amount is added to `payments_approved_amount_total` for its currency. A rejected payment increments `payments_rejected_total`. No separate failed counter is added. `approval_rate` is derived as `payments_approved_total / (payments_approved_total + payments_rejected_total) * 100`; pending and failed payments are excluded. When `payments_approved_total + payments_rejected_total == 0`, `approval_rate` is `null`, meaning insufficient information rather than 0%. The rate is computed from existing counters and is not persisted as an additional metric. R6 cumulative, no-window, and currency-separation rules remain unchanged.
23. **Outbox Publisher v1 topology**: there is exactly one Outbox Publisher instance in v1. It publishes pending records sequentially in insertion order and preserves the order of events for the same payment. Concurrency across multiple publisher instances is deferred and is not implemented in v1.
24. **Outbox pending visibility**: the pending outbox count is obtained from the `payments_db` outbox table and emitted as point-in-time snapshots in the Outbox Publisher's existing structured JSON logs. A snapshot is emitted on every polling cycle, including retry cycles while Kafka is unavailable, and immediately after a record is successfully marked published in PostgreSQL, not merely after the Kafka acknowledgement; emission is per cycle even when the count is unchanged. The latest entry reflects the last completed cycle or publish mark, with no real-time or seconds-based freshness guarantee and the polling interval still configurable. Log volume grows with polling frequency; no previous-count state, endpoint, metric, service, database, or configuration is added. The Observability API keeps its existing operational sources and does not read `payments_db`; readiness remains dependency-only.

## Capabilities

### New Capabilities

- `local-infrastructure`: reproducible local Kafka 4.x (KRaft) and PostgreSQL runtime with the seven agreed logical databases, per-service database ownership including the Workers API's exclusive `workers_api_db`, the two listeners, disabled topic auto-creation, explicit topic initialization, health and readiness checks, structured JSON logs, and reset.
- `payment-api`: payment creation, `Idempotency-Key` semantics, validation, HTTP 202 after the database commit, and atomic transactional outbox writes.
- `outbox-publisher`: reliable at-least-once publication of `PaymentRequested` events to `payments.events` with broker acknowledgement before marking records published, a single publisher instance in v1, sequential publication in insertion order that preserves per-payment ordering, and point-in-time pending-count snapshots in existing structured JSON logs emitted on every polling cycle, on retry cycles while Kafka is unavailable, and after each successful publish mark, with no new endpoint, metric, or configuration.
- `simulated-payment-provider`: deterministic agreed charge scenarios and idempotent charge processing keyed by `paymentId`.
- `payment-worker`: `PaymentRequested` consumption, provider calls, three-attempt retry policy, `PaymentApproved`/`PaymentRejected` publication, and categorized `payments.dlq` routing for processing and validation failures.
- `observability-api`: payment read projection, event history, and operational dead-letter records written by internal consumers in `observability_db`, processing-only `FAILED` projection, validation-dead-letter inspection, DLQ deduplication by `eventId` plus category or original Kafka coordinates, consumer-group queries, and operational information without cross-service SQL.
- `notification-workers`: simulated, log-only notifications driven by `PaymentApproved` and `PaymentRejected` events, with structured JSON lifecycle logs for reception, processing, duplicates, simulation, and failures.
- `analytics-workers`: cumulative `payments_requested_total`, `payments_approved_total`, `payments_rejected_total`, and per-currency `payments_approved_amount_total` metrics computed and persisted transactionally in `analytics_db` from `PaymentRequested`, `PaymentApproved`, and `PaymentRejected`, plus a derived approval rate from approved and rejected counters; no time windows, currency conversion, failed counter, or additional persisted metric.
- `workers-api`: 5-second heartbeat polling and 15-second offline liveness, heartbeat-delivered commands, per-worker-instance fault injection with exactly four injectable types (`processing-error`, `slow-processing`, `crash-before-processing`, `crash-after-processing`), where `pause` and `resume` are control commands rather than fault types, `slow-processing` is available to all four worker types, client-provided `clientConfigKey` values map to internal UUID v4 `faultId` values persisted with deletion status in the exclusive `workers_api_db`, active configuration including `always` faults remains volatile, an active key submitted with a different `workerType` or `faultType` receives HTTP 409 Conflict, a lost creation race receives HTTP 409 Conflict without generating a `faultId` or changing the winner's association, a same-identity resubmission updates the active configuration without changing the association or `faultId`, and a missing or invalid key receives HTTP 400 Bad Request.

### Modified Capabilities

None. The project has no existing capability specs.

## Impact

- New Go services in a single root Go module with narrow shared `internal/` technical packages; no `go.work` and no shared business logic. No existing application code is modified.
- New Docker Compose topology, one PostgreSQL instance with seven logical databases, and two Kafka topics.
- New HTTP and Kafka contracts between services.
- New local run, reset, and experiment documentation.
- All runtime dependencies remain local; no paid or managed cloud services are required.
- The former blocking questions are resolved: provider scenarios are global, idempotency-key behavior is fixed, exhausted retries project as `FAILED` while validation failures do not, the local security posture is fixed, the Go module layout is fixed, notification logging is fixed, the initial Analytics metric set is fixed, the worker heartbeat parameters are fixed, the DLQ identity and recovery limit are fixed, and the Analytics state treatment and approval rate are fixed. All decisions R1-R10 are approved. The `once` fault persistence mechanism is decided: each worker owns its `once` records in its own logical database and registers the record atomically immediately before the fault's injection point. Fault-configuration identity is decided: clients supply a stable `clientConfigKey`, the Workers API generates an internal `faultId`, and the association is persisted in its exclusive `workers_api_db`, so reusing the key after a restart keeps the same `faultId`; a key with no non-deleted association creates a new rule and a new `faultId`, deletion does not delete worker `once` records, and historical records keep their original `faultId`. All identity details are now approved: global uniqueness across non-deleted associations enforced atomically by PostgreSQL at creation time, concurrent creation races yielding one winner and HTTP 409 Conflict for losers without extra `faultId` or association changes, distinct clear and delete operations where clear preserves the non-deleted association and `faultId` while delete retains the historical association and frees the key, same-identity updates that preserve the original `faultId` and once history, HTTP 409 Conflict for incompatible active keys, HTTP 400 Bad Request for missing or invalid keys, the case-sensitive 1-128 character ASCII key format, and UUID v4 `faultId` generation. The final documentation review also fixes that Analytics consumes all three lifecycle events, the four injectable fault types with `pause`/`resume` as control commands, the single sequential Outbox Publisher in v1, the `null` approval rate when there are no definitive outcomes, the no-identity DLQ handling, the `POST /charge` provider endpoint, and the `docker-compose.yml` filename. They do not reopen the approved architecture.

## First-version success criteria

A learner can start the local stack, submit a payment with an idempotency key, and observe HTTP 202 after the database commit while `PaymentRequested` moves through the outbox and `payments.events` to the Payment Worker and provider, producing `PaymentApproved` or `PaymentRejected`. The Observability API projection reflects the terminal status and history, Notification Workers consume the outcomes, Analytics Workers consume all three lifecycle events, a replay with the same idempotency key returns the original payment without duplication, a selected transient provider scenario exercises the three-attempt retry policy, and an exhausted message appears in `payments.dlq` and projects as `FAILED`. An invalid or version-incompatible event is dead-lettered as a validation failure, records `attempts=0`, and does not change payment status. While Kafka is unavailable, a committed payment remains pending in the outbox and retry-cycle snapshots in the publisher's structured JSON logs report it; after Kafka returns, the records are published and marked in PostgreSQL and the snapshot emitted after the successful mark reports the decrease.

- Approved scope, capability boundaries, and implementation order come from the request and the project context.
- `design.md` distinguishes approved constraints, approved architecture decisions, proposed implementation details, and deferrable questions.
- No implementation starts until the user approves this change. R1-R10 are approved and no approved decision blocks the proposal as a whole. The identity lifecycle is fully decided: `clientConfigKey`, UUID v4 `faultId`, the association and its deletion status in `workers_api_db`, global uniqueness across non-deleted associations enforced atomically by PostgreSQL at creation time, HTTP 409 Conflict for creation races and incompatible active keys, HTTP 400 Bad Request for missing or invalid keys, key format, clear preserving the non-deleted association and `faultId`, deletion with key reuse, same-identity updates preserving the original `faultId` and historical `once` records, historical `once` record retention, and per-worker record ownership. Active configuration remains volatile and must be resubmitted after a Workers API restart, reusing the key of a non-deleted rule. None of these errors modifies an association or generates a `faultId`; no identity decision remains pending.
