# Design

## Context

See `proposal.md` for motivation. The repository has no application code yet; this design establishes the first runnable architecture. The requirements live in `specs/` and are not restated here.

This document separates three kinds of content:

- **Approved architecture**: fixed decisions from the project context and the review. They are not open for reinterpretation in this change.
- **Proposed implementation details**: how the approved architecture will be realized. They do not change the approved decisions.
- **Deferrable questions**: implementation choices the review left open. They are listed at the end; some gate specific phases, but none reopens an approved decision.

## Goals / Non-Goals

**Goals:**

- A learner can start the whole laboratory with one Compose command and reset it to a clean baseline.
- Every payment demonstrably moves through the transactional outbox, `payments.events`, the Payment Worker, and the Simulated Payment Provider to a projected terminal state.
- Retries, duplicates, consumer lag, dead letters, and fault injection are observable rather than hidden.
- Each service has a clear responsibility and data boundary.
- The first version stays small enough to read, run, and debug locally.

**Non-Goals:**

- Production hardening: no authentication, TLS, multi-broker Kafka, high availability, or horizontal scale requirements.
- Real payment provider integration.
- Dashboards, Grafana, Loki, Alloy, or any additional observability infrastructure.
- Cloud, Kubernetes, or managed services.
- Exactly-once processing guarantees. The lab teaches at-least-once delivery with idempotent consumers.

## Approved Architecture

These decisions are fixed and must not be reopened without explicit user approval.

1. **PostgreSQL topology**: one local instance with exactly seven logical databases: `payments_db`, `payment_worker_db`, `provider_db`, `observability_db`, `analytics_db`, `notification_db`, and `workers_api_db`. No additional databases are introduced. `payments_db` has the Payment API as its sole logical owner for its payments, idempotency, and outbox data. The Outbox Publisher has authorized technical access restricted exclusively to the `payments_db` outbox table to query pending publications and mark records published after Kafka acknowledgement; it has no access to the payments or idempotency tables, and no other service has access to `payments_db`. `workers_api_db` belongs exclusively to the Workers API and persists the association between client-provided `clientConfigKey` values and internal `faultId` values, including the association's deletion status; it does not store worker `once` records or general configuration state.
2. **Kafka topics**: `payments.events` carries `PaymentRequested`, `PaymentApproved`, and `PaymentRejected`. `payments.dlq` carries exhausted processing events and validation-failed events. Both topics use three partitions and replication factor 1. `payments.events` retains events for seven days; `payments.dlq` retains events for 30 days.
3. **Event envelope**: every event uses `eventId`, `eventType`, `schemaVersion`, `paymentId`, `correlationId`, `occurredAt`, `producer`, and `data`.
4. **Payment status ownership and values**: the Observability API owns the payment read projection and history in `observability_db`. Payment statuses are `PENDING`, `APPROVED`, `REJECTED`, and `FAILED`. `REJECTED` means the provider explicitly rejected the payment for business reasons. `FAILED` means processing could not complete after retries were exhausted and the request was sent to `payments.dlq`. Validation dead letters do not change payment status and remain inspectable. The Payment API does not consume result events to update its own payment status.
5. **Observability access**: the Observability API's HTTP query endpoints are read-only and answer payment and history queries from `observability_db` without cross-service SQL; its internal Kafka consumers write projection state, history, operational dead-letter records, and `once` records to `observability_db`.
6. **Workers API control channel**: workers poll the Workers API through heartbeats and receive pending commands in heartbeat responses. There are no HTTP callbacks and no worker control addresses.
7. **Fault injection**: configuration is per worker instance and supports `once` and `always` modes. `once` means at most one execution per matching message: each message that matches the configuration can receive the fault once, other matching messages remain eligible, and once registered the fault is not applied again to that same message, including after a crash and worker restart. The information required to enforce this must be persisted outside worker memory; each worker stores it in its own logical database, keyed by worker type, `faultId`, Kafka topic, partition, and offset. The record is registered atomically immediately before the fault's injection point. If the worker stops after registration commits but before the fault executes, the record remains and redelivery skips the fault, so `once` guarantees at most one execution per matching message but does not guarantee that the fault executes. Each fault configuration has two identities: a client-provided `clientConfigKey` that names the logical rule and a UUID v4 `faultId` generated by the Workers API. The Workers API persists the `clientConfigKey`-to-`faultId` association and its deletion status in `workers_api_db`, its exclusive database. `clientConfigKey` uniqueness is global within Workers API across non-deleted associations and is enforced atomically by PostgreSQL, not only by Workers API pre-validation. When two concurrent creation requests target the same absent key, exactly one creates the association and returns its `faultId`; each loser receives HTTP 409 Conflict, generates no other `faultId`, and does not modify the winner's association. A creation-race 409 is distinct from an identity-conflict 409; requests that find an existing association follow the approved same-identity update and identity-mismatch rules. Reconfiguring an existing non-deleted rule requires reusing its `clientConfigKey` and recovers its `faultId`, including after a Workers API restart. A new logical rule uses a `clientConfigKey` with no non-deleted association, including a key retained by a deleted historical association, and receives a new UUID v4 `faultId`. If an active key is submitted with a different `workerType` or `faultType`, Workers API rejects the request with HTTP 409 Conflict, leaves the association unchanged, and generates no `faultId`. If both fields match, the request updates the same logical configuration: Workers API preserves the association and original `faultId`, creates no new association or UUID, and updates the active in-memory parameters defined by the contract, including `mode`, worker instance target when applicable, `slow-processing` duration when applicable, and any other parameter already defined for that `faultType`. Changing `once` to `always` or `always` to `once` does not delete, modify, or reset historical `once` records. The updated active configuration remains volatile and is not restored automatically after a Workers API restart. Clearing a fault removes only the active in-memory configuration; the `clientConfigKey`-to-`faultId` association remains active and non-deleted in `workers_api_db` with the same `faultId`, so reconfiguring that rule with the same key recovers the original `faultId`. Deleting a configuration also removes any active configuration, marks its association as deleted while retaining it as historical data with the same `faultId`, and frees the key for a new configuration, which receives a new UUID v4 `faultId`. Clearing or deleting a configuration does not delete or modify worker `once` records, which keep their original `faultId`. A `clientConfigKey` is 1 to 128 ASCII characters limited to letters, digits, hyphen (`-`), underscore (`_`), and dot (`.`), with no spaces, and is case-sensitive. A missing `clientConfigKey` or one that fails this format receives HTTP 400 Bad Request. None of these validation or conflict errors modifies an existing association or generates a `faultId`. `always` keeps applying the fault until the configuration is cleared or the Workers API restarts, writes no such record, and its active configuration remains volatile. Active configurations are not restored automatically after a restart. The only injectable fault types are `processing-error`, `slow-processing`, `crash-before-processing`, and `crash-after-processing`. In v1, `processing-error` is available only for the Payment Worker; Notification, Analytics, and Observability do not support it, and no additional retry policy is introduced for them. `pause` and `resume` are control commands, not fault types. `slow-processing` is available to all four worker types: Payment Worker, Notification Workers, Analytics Workers, and the Observability consumers of events and dead-letter records, and each worker applies the delay before executing its processing logic. In the Payment Worker, `processing-error` and `slow-processing` are injected before calling the simulated provider, and the provider is not called before their behavior completes. `slow-processing` duration is configurable with a 5-second default, does not fail processing, does not trigger retries by itself, and does not alter offset-commit behavior. Fault injection is separate from provider scenario selection and does not change the provider's global scenario.
8. **Payment retries**: three total attempts, with 1-second and 2-second exponential backoff. No jitter.
9. **Provider scenarios and idempotency**: the agreed scenarios are `normal`, `slow`, `timeout`, HTTP 503, permanent rejection, and uncertain result. Scenario configuration is global to the provider and applies to all incoming charge requests until changed or reset; per-payment targeting is deferred. Provider idempotency uses `paymentId`.
10. **Idempotency keys**: one global key namespace, with no expiration in v1. The same key with the same request content returns the original payment. The same key with different content returns HTTP 409 Conflict. A missing `Idempotency-Key` header is a request-structure error and returns HTTP 400 Bad Request. Invalid request content with the header present returns HTTP 422 Unprocessable Content.
11. **Payment API acknowledgement**: after the atomic `payments_db` transaction commits, the API returns HTTP 202 Accepted without waiting for Kafka publication or outbox processing.
12. **Dead-letter semantics**: `failureCategory=processing` covers processing failures, including an injected `processing-error` applied before the provider call, records `attempts=3`, and produces terminal `FAILED`; `failureCategory=validation` covers invalid or version-incompatible events, records `attempts=0`, performs no provider call, and does not produce `FAILED`. The original offset is committed only after broker acknowledgement of the DLQ publication. A crash between publication and commit may duplicate DLQ records; Observability deduplicates them using the approved identity and recovery-limit strategy in decision 21.
13. **Kafka runtime**: Apache Kafka 4.x in KRaft mode with a single broker; external listener `localhost:9092`, internal listener `kafka:9093`; automatic topic creation disabled. Producers use `acks=all`, idempotence enabled, and `min.insync.replicas=1`. Health checks use broker metadata.
14. **Analytics consistency**: Analytics Workers consume `PaymentRequested`, `PaymentApproved`, and `PaymentRejected`, deduplicate lifecycle events by `eventId`, and update their metrics transactionally.
15. **Logging and endpoints**: every service emits structured JSON logs to stdout/stderr and exposes health and readiness endpoints. Loki, Grafana, Alloy, and dashboards remain out of scope.
16. **Local security posture**: the first local version has no service authentication and no TLS, is intended exclusively for local development, and does not expose services to external networks. Kafka and PostgreSQL are reachable from containers and, when needed, from the Mac through host ports published exclusively on localhost. Kafka listeners may bind `0.0.0.0` inside the container to accept Docker connections, but that does not authorize publishing host ports on all interfaces. No production security mechanisms are included in this stage.
17. **Go module layout**: the repository uses one Go module at its root with a single `go.mod`; `go.work` and multiple Go modules are excluded. Each service has its own `main.go` and can compile, run, test, and deploy independently while retaining its own responsibilities and business logic. Shared packages are limited to genuinely common technical concerns such as Kafka and PostgreSQL connectivity, structured logging, and shared event contracts and serialization, with narrow APIs. Services depend only on what they need. Business logic is not shared between services and premature abstractions are excluded. Shared internal packages live under `internal/`; `pkg/` is not created without a concrete need.
18. **Notification logging**: the Notification Worker uses the project's structured JSON logging to stdout. It logs the lifecycle events `event_received`, `event_processed`, `notification_simulated`, `event_ignored_duplicate`, and `event_processing_failed`, including `timestamp`, `level`, `service`, `workerId`, `eventId`, `paymentId`, and `eventType` when available. Logs distinguish reception, processing, duplicate detection, and errors. `notification_simulated` indicates only that a notification was simulated; it does not imply a real email or SMS. `notification_db` is used exclusively for `once` fault records; no notification persistence and no persistent business-event deduplication are introduced, and the approved in-memory deduplication strategy is unchanged.
19. **Analytics initial metrics**: the approved v1 metric set is `payments_requested_total`, `payments_approved_total`, `payments_rejected_total`, and `payments_approved_amount_total`. The counters update from `PaymentRequested`, `PaymentApproved`, and `PaymentRejected` respectively, and approved amounts are grouped by currency. Metrics are cumulative with no time windows in v1. Amounts remain separated by currency and are never converted. `eventId` deduplication and the transactional update of processed records plus metrics are unchanged. No additional metrics are added.
20. **Worker heartbeat parameters**: workers send a heartbeat every 5 seconds. The Workers API marks a worker `offline` when more than 15 seconds have elapsed since the last heartbeat it received from that worker.
21. **DLQ identity and recovery limit**: when the original event contains `eventId` and the record has `failureCategory`, the DLQ identity is `eventId + failureCategory`. When `eventId` is absent, the identity is `sourceTopic + sourcePartition + sourceOffset + failureCategory`. A missing `failureCategory` defaults to `unknown`, including when both `eventId` and `failureCategory` are absent, in which case the original Kafka coordinates plus `unknown` are used. If neither `eventId` nor reliable original coordinates can be recovered, identification and deduplication are not guaranteed: a critical error is logged, the record is not incorporated into the Observability projection, the offset is committed so processing continues with later messages, and the original record remains in Kafka subject to the configured retention. No additional recovery mechanisms or artificial identifiers are introduced. The design does not guarantee automatic recovery from every imaginable failure.
22. **Analytics state treatment and approval rate**: every requested payment increments `payments_requested_total`. Pending and failed payments count only as requested and do not increment approved or rejected counters or the approved amount. An approved payment increments `payments_approved_total` and its amount is added to `payments_approved_amount_total` for its currency. A rejected payment increments `payments_rejected_total`. No separate failed counter is added. `approval_rate` is derived as `payments_approved_total / (payments_approved_total + payments_rejected_total) * 100`; pending and failed payments are excluded. When `payments_approved_total + payments_rejected_total == 0`, `approval_rate` is `null`, meaning insufficient information rather than 0%. The rate is computed from existing counters and is not persisted as an additional metric. R6 cumulative, no-window, and currency-separation rules remain unchanged.
23. **Outbox Publisher v1 topology**: there is exactly one Outbox Publisher instance in v1. It publishes pending records sequentially in insertion order and preserves the order of events for the same payment. Concurrency across multiple publisher instances is deferred and is not implemented in v1.
24. **Outbox pending visibility**: a learner can determine how many outbox records remain pending publication from point-in-time snapshots the Outbox Publisher emits in its existing structured JSON logs. The count is derived only from the `payments_db` outbox table under the publisher's restricted technical access in decision 1. A snapshot is emitted on every polling cycle, including retry cycles while Kafka is unavailable, and immediately after a record is successfully marked published in `payments_db`, not merely after the Kafka acknowledgement. Emission is per cycle even when the count is unchanged, with no special outage-detection emission and no state for remembering a previous count. Each entry reflects the state observed through the last completed polling cycle or successful publish mark; no real-time update or maximum freshness in seconds is guaranteed, and the polling interval stays configurable with no new fixed value. Log volume grows with polling frequency. No additional database, service, HTTP endpoint, metric, or configuration is introduced; only the defined structured JSON logs are reused. The Observability API keeps its existing Kafka-administration and Workers API operational sources and does not read `payments_db`; health and readiness endpoints remain limited to liveness and dependency availability.

Additional fixed constraints: local only; Go; single root Go module with no `go.work`; Apache Kafka 4.x; Docker Compose using `docker-compose.yml`; seven logical PostgreSQL databases, including a Workers API database for `clientConfigKey`-to-`faultId` associations and their deletion status; Kafka in KRaft mode with the specified listeners; explicit topic creation; producers with `acks=all` and idempotence; independent services; Transactional Outbox with a single sequential Outbox Publisher in v1; at-least-once delivery; structured JSON logs, including the Outbox Publisher's per-cycle and post-mark pending-count snapshots from the outbox table with no real-time freshness guarantee; notification lifecycle logs; cumulative Analytics metrics without time windows; currency-separated amounts without conversion; 5-second worker heartbeats with a 15-second offline threshold; DLQ identity by `eventId` plus category or original Kafka coordinates, with `unknown` as the missing-category default and no artificial identifiers; exactly four injectable fault types with `pause`/`resume` treated as control commands; `once` per-message tracking persisted by each worker in its own logical database and registered atomically immediately before its fault-specific injection point; `processing-error` limited to the Payment Worker in v1; `slow-processing` configurable with a 5-second default; worker containers restarted by Docker Compose `restart: on-failure`; health and readiness endpoints; no service authentication or TLS; localhost-only host port publication; deferred dashboard, Grafana, Loki, and Alloy.

## Proposed Architecture

The following details implement the approved architecture. They do not modify it.

### Service topology

```
Client
  │  POST /payments  (Idempotency-Key)
  ▼
Payment API ── one transaction ──▶ payments_db: payments + idempotency + outbox
                                         │
                                Outbox Publisher ──▶ payments.events
                                                          │
                         ┌────────────────────────────────┼───────────────────────────────┐
                         ▼                                ▼                               ▼
                  Payment Worker                  Observability projection        Notification Worker
                         │                                │                               │
                         │──HTTP──▶ Simulated Provider    │                               │
                         │                                ▼                               ▼
                         ├──▶ payments.events        observability_db            simulated log output
                         │    (Approved/Rejected)
                         └──▶ payments.dlq                                        Analytics Worker
                                                                                         │
                                                                                         ▼
                                                                                   analytics_db

Workers API ◀── heartbeat poll ── all workers
      └── heartbeat response: pending commands + per-instance fault configuration
```

The Observability projection consumes both `payments.events` and `payments.dlq`: lifecycle events maintain `PENDING`/`APPROVED`/`REJECTED`, `processing` dead-letter records produce terminal `FAILED`, and `validation` dead-letter records remain available for operational inspection without changing status.

### Deployable units and data ownership

| Unit | Responsibility | Data |
| --- | --- | --- |
| `payment-api` | Payment creation, idempotency, outbox writes | Sole logical owner of `payments_db`: payments, idempotency keys, outbox |
| `outbox-publisher` | Relay outbox records to `payments.events` | No database of its own; authorized technical access restricted to the `payments_db` outbox table to query pending records and mark them published after Kafka acknowledgement, with no access to payments or idempotency tables |
| `simulated-payment-provider` | Charge behavior and scenarios | `provider_db`: charges, scenario state |
| `payment-worker` | Process `PaymentRequested`, retry, publish outcomes, route DLQ | `payment_worker_db`: `once` fault records; no business database; relies on provider idempotency and Kafka offsets |
| `observability-api` | Internal projection and history consumption; read-only HTTP query endpoints | `observability_db`: projection, event history, operational dead-letter records, and `once` fault records written by internal consumers |
| `notification-worker` | Simulated, log-only notifications | `notification_db`: `once` fault records; notifications remain log-only and deduplication remains in memory |
| `analytics-worker` | Business metrics | `analytics_db`: metrics, deduplication records, `once` fault records |
| `workers-api` | Registration, heartbeats, commands, per-instance faults, fault identity persistence | `workers_api_db`: `clientConfigKey`-to-`faultId` associations; active control state and `always` configurations remain in memory; no access to worker `once` records |

The Payment API is the sole logical owner of `payments_db` and its payments, idempotency, and outbox data. The Outbox Publisher is the only other process with any access to `payments_db`, and that technical access is restricted exclusively to the outbox table: it queries pending publications and marks rows published only after Kafka acknowledgement. It has no access to the payments or idempotency tables, and no other service accesses `payments_db`. The publisher runs as a single instance in v1 and publishes pending rows sequentially. All other service data access stays within the owning service.

`once` fault records live in each worker's own logical database: `payment_worker_db` for the Payment Worker, `notification_db` for the Notification Worker, `analytics_db` for the Analytics Worker, and `observability_db` for the Observability projection consumer. No shared fault database is used, and the Workers API does not access these records.

The Workers API control state remains in memory, except the `clientConfigKey`-to-`faultId` associations, which the Workers API persists in `workers_api_db`. Active fault configuration, including `always` faults, remains volatile and is lost on restart, so faults must be configured again. The per-message record that a `once` fault has already been registered for that message must survive worker restarts and is therefore persisted by each worker in its own database, identified by worker type, `faultId`, Kafka topic, partition, and offset. The Workers API never accesses those worker records.

Go layout (approved): one module at the repository root with a single `go.mod` and no `go.work`. Each deployable unit has its own `cmd/<service>` entry point and `main.go`, can build, run, test, and deploy independently, and keeps its own business logic. Shared `internal/` packages are limited to narrow technical concerns such as Kafka, PostgreSQL, structured logging, and event contracts/serialization. Services depend only on the shared packages they need; no `pkg/` directory or shared business logic is introduced without a concrete need.

### Kafka model

| Topic | Producers | Consumers | Purpose |
| --- | --- | --- | --- |
| `payments.events` | Outbox Publisher (`PaymentRequested`), Payment Worker (`PaymentApproved`, `PaymentRejected`) | Payment Worker (`PaymentRequested`), Observability API projection (all three), Notification Worker (`PaymentApproved`, `PaymentRejected`), Analytics Worker (all three) | Payment lifecycle events |
| `payments.dlq` | Payment Worker | Observability projection (`processing` category for `FAILED`; all records for operational inspection) | Exhausted processing events and validation failures |

Fixed topic settings: both topics use three partitions and replication factor 1. `payments.events` uses seven-day retention; `payments.dlq` uses 30-day retention. `min.insync.replicas` is 1, and automatic topic creation is disabled.

Proposed keys and delivery:

- Partition key is `paymentId` so all lifecycle events for one payment stay ordered.
- All producers use `acks=all` and idempotence enabled; the Outbox Publisher and Payment Worker wait for broker acknowledgement before considering a publication successful.
- All consumers use explicit consumer groups and commit offsets after handling.
- Duplicate delivery is expected; consumers deduplicate lifecycle events by `eventId`, and terminal projection updates also deduplicate by `paymentId` and `eventType`. DLQ records use the approved identity strategy in decision 21, including the `unknown` category default and the original Kafka-coordinate fallback; when identity cannot be recovered, deduplication is not guaranteed.
- The Payment API is not a Kafka consumer.

### Event envelope

```json
{
  "eventId": "uuid",
  "eventType": "PaymentRequested | PaymentApproved | PaymentRejected",
  "schemaVersion": 1,
  "paymentId": "uuid",
  "correlationId": "uuid",
  "occurredAt": "RFC3339 timestamp",
  "producer": "service name",
  "data": {}
}
```

`correlationId` is propagated from `PaymentRequested` to its resulting lifecycle events so a learner can correlate a request with its outcome.

### Payment lifecycle and projection

- Payment API writes a payment with initial status `PENDING` in `payments_db` and emits `PaymentRequested`.
- Observability consumes `PaymentRequested` and creates or updates the projection with status `PENDING`.
- Payment Worker emits `PaymentApproved` when the provider approves or `PaymentRejected` when the provider explicitly rejects the payment for business reasons.
- Observability consumes those events and updates the projection to `APPROVED` or `REJECTED`, appending each event to history.
- Processing failures: after three failed attempts, Payment Worker sends the original `PaymentRequested` to `payments.dlq` with `failureCategory=processing`, `attempts=3`, `lastError`, and `failedAt`. Observability consumes that record, sets the projection to terminal `FAILED`, and appends a failure entry to history. No new event type is introduced: the dead-letter record is the failure signal.
- Validation failures: invalid or version-incompatible events are sent directly to `payments.dlq` with `failureCategory=validation`, `attempts=0`, `lastError`, and `failedAt`, without a provider call. Observability records the failure for operational inspection but does not set `FAILED` and does not append a payment status transition.
- `FAILED` is distinct from `REJECTED`: it means processing could not complete after retries were exhausted, not that the provider made a business rejection.
- Terminal statuses are not overwritten by later or delayed lifecycle updates. If a `processing` dead-letter record is observed before the corresponding `PaymentRequested`, the projection remains `FAILED` when that request event arrives; it also remains `FAILED` if a delayed `PaymentApproved` or `PaymentRejected` arrives later.
- DLQ records may be duplicated after a crash between publication and offset commit. Observability deduplicates them using decision 21: `eventId + failureCategory` when `eventId` is present, defaulting a missing category to `unknown`; otherwise `sourceTopic + sourcePartition + sourceOffset + failureCategory`, also defaulting to `unknown`. When neither `eventId` nor reliable original coordinates can be recovered, identification and deduplication are not guaranteed: a critical error is logged, the record is not incorporated into the projection, the offset is committed to continue with later messages, the original record remains in Kafka subject to retention, and no additional recovery mechanism or artificial identifier is introduced. The design does not guarantee automatic recovery from every imaginable failure.

### Payment API

- `POST /payments` with required `Idempotency-Key`; the body carries amount in minor units and a currency.
- The idempotency-key namespace is global across clients, and keys do not expire in v1.
- A missing `Idempotency-Key` header returns HTTP 400 Bad Request without creating a payment.
- Invalid request content with the header present returns HTTP 422 Unprocessable Content without creating a payment.
- The idempotency store records the key, a hash of the request content, the payment identifier, and the response snapshot.
- Same key and same request content: return the stored original payment. Same key and different valid content: return HTTP 409 Conflict.
- Insert the payment, the idempotency record, and the `PaymentRequested` outbox record in one `payments_db` transaction.
- Return HTTP 202 Accepted after that transaction commits. Do not wait for Kafka publication or for the Outbox Publisher.
- A unique constraint on the idempotency key resolves concurrent duplicate requests; the loser reads and returns the winner's result.
- The Payment API does not expose the read projection and does not consume outcome events. Observability is the payment query surface.

### Outbox Publisher

- Poll unpublished outbox rows in insertion order with a bounded batch.
- Run exactly one Outbox Publisher instance in v1. Publish pending rows sequentially and do not implement coordination or concurrency across multiple publisher instances; multi-instance experimentation is deferred.
- Preserve the recording order of events for the same payment; because the publisher is sequential and uses `paymentId` as the key, later events for one payment are not published ahead of earlier ones.
- Publish `PaymentRequested` to `payments.events` with `paymentId` as the key, wait for broker acknowledgement, then mark the row published.
- On broker errors, back off and retry without marking.
- Emit a point-in-time snapshot of the unpublished outbox rows in the existing structured JSON logs on every polling cycle over the outbox table, including retry cycles while Kafka is unavailable, and immediately after a row is successfully marked published in `payments_db` rather than merely after the Kafka acknowledgement. Emit per cycle even if the count is unchanged, add no special outage-detection emission, and keep no previous-count state; count only from the outbox table under the restricted access in decision 1.
- Treat each emitted value as a snapshot through the last completed cycle or publish mark; claim no real-time or seconds-based freshness, leave the polling interval configurable with no new fixed value, and accept that log volume grows with polling frequency.
- Do not add an HTTP endpoint, metric, database, service, or configuration for this count; health and readiness keep their liveness and dependency roles.
- A crash after acknowledgement but before marking causes a duplicate publish after restart. This is accepted; consumers deduplicate.

### Simulated Payment Provider

- `POST /charge` with `paymentId`, amount, and currency.
- `provider_db` stores a unique charge per `paymentId`; repeated and concurrent requests return the original outcome and never apply a second charge.
- Scenario behavior:
  - `normal`: approve.
  - `slow`: approve after a configured delay that remains within the caller timeout.
  - `timeout`: delay beyond the caller timeout so the caller observes a timeout.
  - HTTP 503: return a transient service-unavailable response.
  - permanent rejection: return a final rejected outcome with a reason.
  - uncertain result: process the charge but return an ambiguous response; a retry with the same `paymentId` returns the stored outcome.
- Scenario selection uses a documented global control mechanism. The selected scenario applies to all incoming charge requests until changed or reset. Per-payment targeting is deferred; the provider does not expose per-payment scenario selection in v1.
- Charge records and reset are exposed through documented local endpoints.

### Payment Worker

- Consume `PaymentRequested` from `payments.events` in the `payment-worker` consumer group.
- Use `paymentId` as the provider idempotency key for the first attempt and every retry. The worker keeps no business database; its only persistence is `once` fault records in `payment_worker_db`; redelivery after restart re-calls the provider safely.
- Retry `timeout`, HTTP 503, and uncertain-result outcomes. Do not retry permanent rejection.
- Make three total attempts, waiting 1 second before attempt 2 and 2 seconds before attempt 3. No jitter.
- `processing-error` is the only fault type restricted to this worker in v1. It is injected before the provider call, so the provider is not called before the forced error behavior completes. It reuses the same three-attempt schedule and, when exhausted, the `processing` DLQ path with `attempts=3`; it does not introduce a separate retry policy.
- `slow-processing` is injected before the provider call, so the provider is not called until the delay completes. It delays processing with a configurable duration and a 5-second default, does not fail processing, does not trigger retries by itself, and does not alter the fixed retry policy or offset-commit behavior.
- `crash-before-processing` and `crash-after-processing` stop the worker without committing the offset. Redelivery relies on provider idempotency by `paymentId` and the stable result `eventId`; the worker has no `eventId` deduplication store, so duplicate detection is not claimed. If the worker crashes after publishing the result, it may publish the same result again with the same `eventId`; this duplicate publication is accepted in v1 and Analytics and Observability deduplicate it.
- Publish `PaymentApproved` or `PaymentRejected` to `payments.events`. Build the result event with a stable `eventId` (derived from `paymentId` and `eventType`) and propagate `correlationId`, so a republished result is deduplicable.
- Publish failure prevents offset commitment and causes reprocessing. Duplicate publication is possible and safe.
- After the three total attempts fail, including when the failure is an injected `processing-error` applied before the provider call, publish the original event with `failureCategory=processing`, `attempts=3`, `lastError`, and `failedAt` to `payments.dlq`, publish no approval or rejection event, and commit the original offset only after the DLQ publication is acknowledged by the broker. The dead-letter record is the signal Observability uses to project `FAILED`.
- For invalid or version-incompatible events, publish to `payments.dlq` with `failureCategory=validation` and `attempts=0` without calling the provider, publish no approval or rejection event, and commit the original offset only after broker acknowledgement. Validation failures do not produce `FAILED`.
- Every DLQ record carries the original event's `sourceTopic`, `sourcePartition`, and `sourceOffset` when those coordinates are available, so Observability can compute the fallback identity in decision 21. `failureCategory` is optional in the contract; this worker sets it for both recognized failure paths, and consumers default an absent value to `unknown`.
- A crash after DLQ acknowledgement but before the original offset commit may republish the DLQ record. Observability must tolerate this duplicate as described above.
- The worker does not persist processing attempts. Observability history is event-based.

### Observability API

- Consume `PaymentRequested`, `PaymentApproved`, and `PaymentRejected` from `payments.events` in a dedicated projection consumer group. These internal consumers write the payment projection and ordered event history to `observability_db`.
- Keep all HTTP query endpoints read-only: they do not modify projection, history, operational dead-letter, `once`, or other persisted state. Projection, history, operational dead-letter, and `once` writes are internal responsibilities of the Observability Kafka consumers in `observability_db`.
- Consume `payments.dlq` in the same projection service. A `failureCategory=processing` dead-lettered `PaymentRequested` marks the payment `FAILED` and appends one failure entry to history; a `failureCategory=validation` record is stored for operational inspection without a status change or payment transition. No additional event type is introduced.
- Deduplicate lifecycle events by `eventId`; apply terminal updates idempotently by `paymentId` and `eventType`. Deduplicate DLQ records using decision 21, so duplicates after a crash do not create duplicate history, status transitions, or operational entries. If neither `eventId` nor reliable original coordinates can be recovered, identification and deduplication are not guaranteed: emit a critical error log, do not incorporate the record into the projection, commit the offset to continue with later messages, and leave the original record in Kafka subject to retention, without introducing an artificial identifier. Terminal statuses (`APPROVED`, `REJECTED`, `FAILED`) take precedence over later or delayed lifecycle updates, including a delayed `PENDING` update and delayed `PaymentRequested`, `PaymentApproved`, or `PaymentRejected` events after `FAILED`.
- Serve payment lookup, payment listing, and payment event history exclusively from `observability_db`.
- Report consumer groups, members, committed offsets, and lag through Kafka administration APIs.
- Report operational information from Kafka administration (topics, DLQ) and from the Workers API over HTTP (worker heartbeat status and active faults). The Workers API read is an HTTP control-plane read, not cross-service SQL. The pending outbox count is not part of this view: the Observability API does not read `payments_db`, and the publisher reports that count in structured JSON logs per decision 24.
- Do not read `payments_db`, `payment_worker_db`, `provider_db`, `analytics_db`, `notification_db`, or `workers_api_db`. Provider charge records remain available from the provider's own endpoint; analytics metrics remain available from the Analytics Worker's own read endpoint; worker and fault state come from the Workers API over HTTP.
- Return partial responses with an explicit unavailable marker when a source cannot be reached.

### Notification and Analytics Workers

- Notification Worker consumes `PaymentApproved` and `PaymentRejected` in its own group and emits simulated notifications through the project's structured JSON logging to stdout.
- It logs `event_received`, `event_processed`, `notification_simulated`, `event_ignored_duplicate`, and `event_processing_failed`, including `timestamp`, `level`, `service`, `workerId`, `eventId`, `paymentId`, and `eventType` when available. The lifecycle records distinguish reception, processing, duplicate detection, and errors.
- `notification_simulated` indicates only that a notification was simulated; it does not imply that a real email or SMS was sent.
- It keeps no business database and no persistent notification records; `notification_db` stores only `once` fault records and is not used for event deduplication. Duplicate suppression remains in-memory for the lifetime of the process, so a restart may re-emit a notification under at-least-once delivery. After `crash-after-processing`, redelivery may emit the notification again because the in-memory record was lost; this is accepted deliberately in v1. No persistent deduplication is introduced.
- Analytics Worker consumes `PaymentRequested`, `PaymentApproved`, and `PaymentRejected` in its own group, deduplicates events by `eventId`, and updates the approved metric set transactionally in `analytics_db`: `payments_requested_total` for requested payments, `payments_approved_total` for approvals, `payments_rejected_total` for explicit rejections, and `payments_approved_amount_total` for approved amounts grouped by currency. The metrics are cumulative with no time windows in v1. Amounts remain separated by currency and are not converted.
- Every requested payment counts in `payments_requested_total`. Pending and failed payments count only as requested; they do not increment the approved or rejected counters or the approved amount. No separate failed counter is added. `approval_rate` is derived as `payments_approved_total / (payments_approved_total + payments_rejected_total) * 100`, excluding pending and failed payments, and is not persisted as an additional metric. When the denominator is zero, `approval_rate` is `null`, meaning insufficient information rather than 0%.
- Analytics metrics are served by the Analytics Worker's own documented read endpoint, including the derived `approval_rate`, which is `null` when no definitive outcomes exist. The Observability API does not query `analytics_db`.
- `FAILED` is projected from `payments.dlq` and is not an additional lifecycle event. A failed payment counts only as requested and remains distinct from `REJECTED`; failure does not imply that the provider did not charge. Notification Workers continue to consume `PaymentApproved` and `PaymentRejected` only. No separate failed counter or additional persisted metric is introduced. No separate failed event is introduced.
- Neither worker shares a consumer group with the Payment Worker, so backlog or failure stays isolated.

### Workers API and fault injection

- The Workers API keeps registration, heartbeat, command, and active fault configuration state in memory, except the `clientConfigKey`-to-`faultId` associations and their deletion status, which it persists in its exclusive `workers_api_db`. The per-message `once` record is owned by each worker in its own database and is never stored by the Workers API.
- Clear and delete are distinct operations. Clearing removes the active in-memory fault configuration, leaves the association active and non-deleted in `workers_api_db` with the same `faultId`, allows the same key to recover that `faultId` on reconfiguration, and leaves historical `once` records unchanged. Deleting also removes any active configuration, marks the association as deleted while preserving its historical `faultId`, frees the key for a new UUID v4 `faultId`, and leaves historical `once` records unchanged.
- A request with a non-deleted `clientConfigKey` whose `workerType` and `faultType` match is an update of the active configuration: preserve the association and original `faultId`, create no new association or UUID, and apply the changed contract parameters (`mode`, worker instance target when applicable, `slow-processing` duration when applicable, and other parameters already defined for that `faultType`). Do not delete, modify, or reset historical `once` records, including when switching between `once` and `always` in either direction. A different `workerType` or `faultType` remains HTTP 409 Conflict with no association or `faultId` change. The updated configuration stays volatile and is not restored after a Workers API restart.
- The Workers API may pre-check whether a key is absent, but PostgreSQL is the authority that atomically enforces uniqueness of non-deleted associations at creation time. If concurrent creations for the same absent key race, exactly one wins, returns the association's `faultId`, and continues normally; each loser receives HTTP 409 Conflict, generates no other `faultId`, and leaves the winner's association unchanged. A creation-race 409 is distinct from an identity-conflict 409, and any request that finds an existing association follows the same-identity update or identity-mismatch rules above.
- A worker registers with a stable identity, worker type, and capabilities or version. Registration carries no control address.
- Registered workers poll the Workers API with a heartbeat every 5 seconds. Each heartbeat updates last-seen and its response carries pending commands and the current per-instance fault configuration.
- The Workers API marks a worker `offline` when more than 15 seconds have elapsed since its last received heartbeat.
- Commands target a worker instance, are queued by the API, and are delivered in that worker's next heartbeat response. Each command has an identifier; the worker reports applied identifiers in subsequent heartbeats, and the API removes acknowledged commands. Duplicate delivery does not apply an effect twice.
- Fault injection is configured per worker instance with `once` and `always` modes. The only injectable fault types are `processing-error` (force an error during processing), `slow-processing` (add artificial delay during processing), `crash-before-processing` (simulate a crash before processing the message), and `crash-after-processing` (simulate a crash after processing but before committing the offset). `pause` and `resume` are control commands, not fault types. An `always` fault remains active until it is cleared or the Workers API restarts; because configuration is in memory, a restart loses it and the fault must be configured again. Provider scenario results remain configured through the provider's global scenario selection and are independent of worker fault injection. Configuration is delivered in heartbeat responses; there are no callbacks or control addresses.
- `processing-error` is available only for the Payment Worker in v1; Notification, Analytics, and Observability do not support it, and no additional retry policies are introduced for them. In the Payment Worker it is injected before the provider call. In `always` mode it is injected on every attempt, follows the fixed three-attempt schedule, and uses the `processing` DLQ path; in `once` mode it is injected once per message and later attempts process normally. `slow-processing` is available to all four worker types, applies a configurable delay with a 5-second default before each worker's processing logic (and before the provider call in the Payment Worker), and does not fail processing, cause retries, or alter offset-commit behavior.
- Neither crash fault commits the offset, so Kafka redelivers the message after restart. `once` applies at most once per matching message: each matching message is eligible once, other matching messages remain eligible, and the same message does not receive the fault again after a crash and restart. The record is registered atomically immediately before the fault's injection point: for `crash-before-processing`, before processing starts and immediately before the crash; for `crash-after-processing`, after processing and its effects complete and immediately before the crash; for `processing-error` and `slow-processing`, immediately before the corresponding behavior. If the worker stops after registration but before executing the fault, the record remains and redelivery skips the fault, so at most one execution is guaranteed, not execution itself. Records live in the worker's own database, keyed by worker type, `faultId`, topic, partition, and offset, survive restarts and redeliveries, and are retained for the life of the data with no automatic cleanup in v1. The Workers API generates a UUID v4 `faultId` for each new association with a client-provided `clientConfigKey` and persists the association in `workers_api_db`; reusing the key of a non-deleted rule keeps its `faultId`, deleting marks the association as deleted while keeping its `faultId` and freeing the key, and a rule created with that key receives a new UUID v4 `faultId`. Historical records keep their original `faultId`. `always` writes no such record.
- Redelivery suppression after `crash-after-processing` depends on each consumer's documented mechanism: Observability and Analytics persist `eventId` deduplication; Notification uses in-memory deduplication and may re-emit after a restart, which is accepted in v1; the Payment Worker relies on provider idempotency by `paymentId` and the stable result `eventId`, and may publish the same result again with the same `eventId`. No stronger guarantee is claimed.
- Because control state is in memory, a Workers API restart clears registration, queued commands, and active fault configuration; active `always` faults stop, workers re-register, and faults must be reapplied by resubmitting the `clientConfigKey` of a non-deleted rule to recover its `faultId`. The `clientConfigKey`-to-`faultId` associations survive in `workers_api_db`. The per-message `once` record is not part of that in-memory control state; each worker persists it in its own database so it survives restarts. This is documented as a local-lab limitation.
- Each worker runs in its own container with Docker Compose `restart: on-failure`. A simulated crash terminates the process with an error, Docker restarts the container, the worker reconnects to Kafka, and messages whose offsets were not committed are redelivered. The Workers API does not implement a restart mechanism.

### Local deployment

- One Apache Kafka 4.x container in KRaft mode and one PostgreSQL container.
- Kafka exposes `localhost:9092` to the host and `kafka:9093` to Compose services. Automatic topic creation is disabled.
- Host-published Kafka and PostgreSQL ports bind exclusively to localhost. Kafka listeners may bind `0.0.0.0` inside the container, but no host port is published on all interfaces. Services are not exposed to external networks.
- The first local version has no service authentication or TLS and is intended only for local development. No production security mechanisms are included.
- PostgreSQL initialization creates exactly `payments_db`, `payment_worker_db`, `provider_db`, `observability_db`, `analytics_db`, `notification_db`, and `workers_api_db`, with per-service roles.
- Topic initialization creates `payments.events` and `payments.dlq` with three partitions, replication factor 1, and `min.insync.replicas=1`. `payments.events` retains events for seven days; `payments.dlq` retains events for 30 days.
- Producers use `acks=all` and idempotence enabled.
- One container per application service, plus one-shot initialization for databases, schema, and topics. Each worker container uses Docker Compose `restart: on-failure`, so a simulated crash that exits with an error is restarted by Docker and the worker reconnects to Kafka.
- Health checks gate dependent service startup. Kafka health checks use broker metadata. Every service exposes health and readiness endpoints; readiness reports dependency availability.
- All services emit structured JSON logs to stdout/stderr. No log files, Loki, Grafana, or Alloy are provided.
- A documented reset removes containers and volumes.

## Risks / Trade-offs

- **At-least-once duplicates** → consumers deduplicate lifecycle events by `eventId` and DLQ records by the approved identity strategy in decision 21; the provider is idempotent by `paymentId`; the lab explicitly teaches duplicate handling and states that deduplication is not guaranteed when no reliable identity can be recovered.
- **Polling outbox adds latency** → configurable poll interval; acceptable for an educational lab; a CDC approach would add infrastructure and is excluded.
- **Single Outbox Publisher instance** → sequential publication bounds throughput and provides no publisher redundancy; per-payment ordering is preserved and multi-instance concurrency is deferred.
- **Single PostgreSQL instance with seven logical databases** → per-database roles preserve logical ownership; physical isolation is intentionally out of scope.
- **Payment Worker uses `payment_worker_db` only for `once` fault records** → redelivery safely reuses provider idempotency, and processing-attempt history is not persisted; Observability history is event-based.
- **Notification database is limited to `once` fault records** → notifications are log-only and in-memory deduplication is lost on restart, so duplicates may be re-emitted, including after `crash-after-processing`; this is accepted in v1, and `notification_db` is not used for event deduplication.
- **Workers API database stores only fault identity associations** → `workers_api_db` persists `clientConfigKey`-to-`faultId` associations and their deletion status and is accessible only to the Workers API, while control state, pending commands, active fault configuration, and `always` faults remain in memory and are lost on restart. Per-message `once` tracking is separate: each worker persists it in its own database, the Workers API never stores it, and historical records keep their original `faultId`.
- **Observability projection lag** → the projection is eventually consistent with `payments.events`; the API reports projection lag through consumer-group information.
- **Operational queries depend on the Workers API** → Observed worker and fault state is unavailable when the Workers API is down; the Observability API marks that section unavailable.
- **Single Kafka broker has no fault tolerance** → acceptable locally; broker restarts are themselves an experiment, and pending outbox rows survive; the publisher reports the outstanding count in its existing structured JSON logs on each polling and retry cycle, so no new endpoint, metric, service, or database is needed to observe the outage.
- **Pending count is sampled, not live** → snapshots are emitted per polling cycle and after successful publish marks; log volume grows with polling frequency, the latest entry reflects only the last completed cycle or mark, and no real-time or seconds-based freshness is guaranteed. No previous-count state or new configuration is introduced.
- **A global provider scenario affects every charge** → the selected scenario remains active until changed or reset; reset returns the provider to the default scenario, and per-instance fault injection stays separate from provider scenario selection.
- **Fault injection can leave consumers stuck** → once/always modes, clear-fault controls, resets, and documented recovery steps are required; `once` records are persisted by each worker in its own database.
- **`once` fault tracking requires per-worker persistence** → the worker registers the fault identity atomically immediately before the fault's injection point, keyed by worker type, `faultId`, topic, partition, and offset; records survive restarts and redeliveries and are retained for the life of the data with no automatic cleanup in v1. If the process stops after registration but before execution, the fault is skipped, so at most one execution is guaranteed, not execution itself. Each configuration has a client-provided `clientConfigKey` and an internal `faultId`; the Workers API persists their association in `workers_api_db`, reuses the `faultId` when the same key returns, and creates a new `faultId` for a new key.
- **Fault identity is tied to key lifecycle** → a non-deleted `clientConfigKey` globally identifies one rule and recovers its `faultId`, including after a Workers API restart; an incompatible `workerType` or `faultType` yields HTTP 409 Conflict, a missing or invalid key yields HTTP 400 Bad Request, and none of these errors changes an association or generates a `faultId`; clearing leaves the association active and non-deleted with the same `faultId`, while deleting marks it as deleted without changing its `faultId` and frees the key for a new rule with a new UUID v4 `faultId`; a same-identity resubmission updates the volatile configuration while preserving the association, original `faultId`, and historical `once` records. PostgreSQL atomically enforces this uniqueness for non-deleted associations at creation time: concurrent creations for the same absent key produce one winner and HTTP 409 Conflict for each loser with no extra `faultId` or association change. This preserves historical `once` identity while requiring explicit deletion state, update semantics, atomic uniqueness, and distinct conflict handling.
- **`crash-after-processing` depends on consumer deduplication** → persisted `eventId` deduplication in Observability and Analytics; in-memory deduplication in Notification, which may re-emit after restart and is accepted in v1; and provider idempotency plus the stable result `eventId` in the Payment Worker, which may republish the same result and is also accepted. No stronger guarantee is claimed.
- **Docker Compose restart policy is the only worker recovery mechanism** → each worker runs in its own container with `restart: on-failure`; a simulated crash exits with an error and Docker restarts it, while the Workers API provides no restart control.
- **Time-based experiments are sensitive to clock and timeout settings** → use UTC timestamps and make timeouts configurable and documented.
