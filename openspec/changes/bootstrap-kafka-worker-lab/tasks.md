# Tasks

## 1. Decision status

Approved decisions R1-R10, the four payment statuses, and the two dead-letter categories are recorded in `design.md` and the specs. No approved decision remains pending. The `once` fault persistence mechanism is decided: each worker persists `once` records in its own logical database and registers the identity atomically immediately before the fault's injection point. Fault identity is fully decided: clients supply a `clientConfigKey`, the Workers API generates a UUID v4 `faultId` and persists their association with deletion status in its exclusive `workers_api_db`; uniqueness is global across non-deleted associations and is enforced atomically by PostgreSQL at creation time, a lost creation race receives HTTP 409 Conflict without another `faultId` or association change and is distinct from an identity conflict, an active key with a different `workerType` or `faultType` receives HTTP 409 Conflict, a same-identity resubmission updates the active configuration while preserving the original `faultId` and historical `once` records, keys are case-sensitive with the approved 1-128 character ASCII format, clearing a fault deactivates the in-memory configuration while leaving the association active (non-deleted) with the same `faultId`, and deletion marks the association as deleted without changing its `faultId` while freeing the key for a new rule with a new UUID v4 `faultId`. Clearing or deleting does not delete or modify worker `once` records, which keep their original `faultId`. Active configurations remain volatile and `always` faults are not restored automatically. A missing or invalid `clientConfigKey` returns HTTP 400 Bad Request, an incompatible active key returns HTTP 409 Conflict, and none of these errors modifies an association or generates a `faultId`. Implementation still waits for user approval.
